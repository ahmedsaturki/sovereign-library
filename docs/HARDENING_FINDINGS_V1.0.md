## CRITICAL findings

### C-1 — Workflows do not pin actions by SHA and do not declare least-privilege `permissions`

**Files**
- `.github/workflows/android.yml` (line 30: `actions/checkout@v4`, line 33: `actions/setup-java@v4`, line 39: `android-actions/setup-android@v3`, line 47: `gradle/actions/setup-gradle@v4`, line 75: `actions/upload-artifact@v4`)
- `.github/workflows/kotlin-jvm.yml` (lines 30, 33, 39, 71)
- `.github/workflows/python-ports.yml` (lines 37, 38)
- `.github/workflows/verify.yml` (lines 20, 24, 35, 36)
- `.github/workflows/prepare-authorized-release-artifacts.yml` (lines 16, 21, 35)

**Why this matters.** Tag-pinned actions are mutable — a compromised upstream
tag (the `tj-actions/changed-files` incident of 2025-03 is the canonical case)
lets an attacker ship malicious code into our build. Pinning to immutable
commit SHAs is the supply-chain baseline.

Additionally, no workflow declares `permissions:` at the top level. The
GitHub default is `read-all` contents, which is better than the legacy
implicit-write-everything but still gives the runner far more scope than
needed. Jobs that only test should not be able to write to the repo.

**Fix.** Pin every `uses:` reference to the commit SHA matching the current
major tag, and add a top-level `permissions: { contents: read }` block that
individual jobs override only when they genuinely need write (artifact
upload does not require write — it uses the OIDC token and the `id-token:
write` permission only when uploading to a registry).

### C-2 — No secret-management hardening; no OIDC; long-lived PATs are the implied model

**Files**
- `.github/workflows/prepare-authorized-release-artifacts.yml` (entire file)

**Why this matters.** The current authorized-release-artifacts workflow runs
on `workflow_dispatch` only and prepares release tarballs. There is no
provenance attestation, no SLSA level, no signing step. When this workflow
later publishes to GitHub Releases (or to an optional free registry) it will
have to authenticate. If that authentication is implemented as a stored
PAT, the project inherits every long-lived-secret risk: leakage via logs,
exfiltration via PR forks, no expiry, no per-job audit.

**Fix.** Add an OIDC token issuance step (`actions/github-script` calling
`github.getOIDCToken()` or, more directly, `aws-actions/configure-aws-credentials@v4`
style pattern with `id-token: write` permission) wired to whatever cloud or
GitHub Packages target the next release wave selects. Add a separate secret
scanning workflow that fails the build if any likely credential is committed.

### C-3 — Kotlin source in `SafePathResolverAndroid.kt` does not compile

**File**
- `ecosystems/android/safe-path-resolver/src/main/java/org/sovereign/safePathResolver/android/SafePathResolverAndroid.kt`

**Specific defects (verified by re-reading the file end-to-end):**

1. Line 33: `if (value !is String)` — `value` is already typed as `String` in
   the enclosing function signature, so `!is String` is always false. Dead
   branch but not a compile error (Kotlin allows it for non-final types only;
   for `String` it is a warning). Keep but consider removing.
2. Line 49: `Regex("^//\\\\?/[A-Za-z]:(/|$)").find(value)!!` — `!!` on a
   nullable platform result after a `containsMatchIn` predicate is
   defensible but brittle. The regex literals are correct (double-escaped
   backslash inside a Kotlin string literal → single backslash in the regex).
3. **Line 57** — `if (value.startsWith("//")) return RootDescriptor(... ...)`:
   the second argument `value.substring(2).split("/").filter { it.isNotEmpty() }`
   is **not followed by a closing paren** before the `return` statement.
   This is a syntax error and the file will not compile.
4. **Line 58** — `if (value.startsWith("/")) return RootDescriptor("absolute", "/", "/", value.substring(1).split("/").filter { it.isNotEmpty() }`:
   the `split(...).filter { ... }` call is **missing the closing paren**
   for `filter`. The whole expression is followed by a newline and then
   line 59 starts with `if (Regex(...))` — so the `if` chain has no
   terminating paren for the `RootDescriptor(...)` constructor. **Syntax
   error.**
5. **Line 60** — `return RootDescriptor("relative", "", "", value.split("/").filter { it.isNotEmpty() }`:
   same defect: `filter { ... }` is missing its closing paren and the
   `return` statement is incomplete. **Syntax error.**
6. **Lines 156, 158, 159, 160, 161** — use of `?` as a binary operator:
   ```kotlin
   "absolute" -> "/${normalizedRoot.root.rest.joinToString("/")}/${candidatePath.absolute ? candidatePath.path : candidatePath.segments.joinToString("/")}"
   ```
   Kotlin has no ternary `? :`; this is Java syntax. The code as written
   will fail to compile with `Expecting an element`. It must be replaced
   with `if (...) ... else ...`.
7. The conformance runner imports the unfixed file: `ecosystems/android/conformance/src/main/java/org/sovereign/conformance/AndroidConformanceRunner.kt` will fail to load against a broken library module.

**Why this matters.** Per `GOVERNANCE.md`, claims of "TECHNICALLY_READY" must
be evidence-backed. A cube whose primary Kotlin source does not compile
cannot be "ready". Per `PROJECT_CONTROL.md` line 37, this cube is
"IN_PROGRESS, not TECHNICALLY_READY until SDK + emulator evidence" — and
that progression is blocked by compile failure alone.

**Fix.** Apply minimal targeted corrections: add the missing closing
parens on lines 57, 58, 60 and replace the Java ternary on lines 156–161
with proper Kotlin `if/else`. Do not refactor the rest of the file.

## HIGH findings

### H-1 — Reproducibility scripts are not guarded against `/tmp` collisions and parallel-job races

**Files**
- `.github/workflows/android.yml` (lines 62–71)
- `.github/workflows/kotlin-jvm.yml` (lines 53–67)

**Why this matters.** Both workflows use `/tmp/aar1`, `/tmp/aar2`,
`/tmp/oot1`, `/tmp/oot2`. On shared self-hosted hardware, parallel runs on
different jobs can race on these paths. On hosted runners the directory is
ephemeral per-job but the script is still vulnerable to: a) `diff` returning
non-zero on a hash mismatch and silently not aborting because there is no
`set -euo pipefail`; b) `find ... | head -1` selecting the wrong AAR if
multiple outputs are present (e.g. after a multi-module build); c) failure
to clean up between attempts.

**Fix.** Add `set -euo pipefail` at the top of every `shell: bash` script
that performs the reproducibility check. Use a per-run subdirectory
under `$RUNNER_TEMP` (which is guaranteed unique) instead of `/tmp`.
Assert exactly one AAR with `find ... -name '*.aar' -print | wc -l` and
abort if it is not 1.

### H-2 — No SBOM generation step in any workflow

**Files**
- All five workflows.

**Why this matters.** A Software Bill of Materials is the dependency-
transparency baseline for any library that aims at "independently
distributable" status. GitHub now generates SBOMs on demand for repos, but
a per-build SBOM attached to the run artifacts is auditable, reproducible,
and suitable for downstream consumers.

**Fix.** Add an `anchore/sbom-action` (or `aquasecurity/trivy-action` with
the `--format spdx-json` flag) step in each release-bearing workflow,
producing SPDX JSON and uploading it alongside the binary artifact.

### H-3 — No dependency vulnerability scan

**Files**
- All five workflows.

**Why this matters.** `trivy fs` and `safety check` are the de-facto
baselines. We have direct gradle and pip dependencies, plus transitive
ones, and no automated scan.

**Fix.** Add `aquasecurity/trivy-action@<sha>` doing `fs` and `rootfs`
scans, plus a Python `safety check` step in `python-ports.yml`. Both
must be non-fatal in CI (advisory mode) but emit SARIF so the Security
tab picks them up; the publishing workflow makes them fatal.

### H-4 — No artifact signing (Sigstore / cosign) and no SLSA provenance

**Files**
- `.github/workflows/prepare-authorized-release-artifacts.yml`

**Why this matters.** The current authorized-release-artifacts workflow
emits tarballs with no signing. When these tarballs become actual GitHub
release assets, downstream consumers cannot verify their integrity
against a known publisher without a signature.

**Fix.** Add `sigstore/cosign-installer` + a `cosign sign-blob` step using
keyless OIDC signing tied to the workflow identity, and emit an SLSA
provenance attestation via `slsa-framework/slsa-github-generator` v2.0.

### H-5 — No YAML lint / no pre-commit hooks

**Files**
- `.yamllint.yml` (does not exist; `.github/` has no `.yamllint.yml` or
  equivalent).

**Why this matters.** Several of the workflow files use inline JSON arrays
mixed with YAML mappings in ways that are easy to break silently (the
`matrix.include:` cell in `python-ports.yml` is one such case). A
lint-on-save / lint-on-pre-commit step prevents regressions.

**Fix.** Add `.yamllint.yml` (relaxed but real), `.pre-commit-config.yaml`
using `pre-commit/pre-commit-hooks`, `adrienverge/yamllint`,
`rhysd/actionlint`, `igorshubovych/markdownlint-cli2`, and (for Kotlin
DSL) the Kotlin linter via `gradle/actions/setup-gradle`.

## MEDIUM findings

### M-1 — No Gradle build cache configured for CI

**File**
- `ecosystems/android/build.gradle`
- `ecosystems/android/gradle.properties` (does not exist)

**Why this matters.** CI re-downloads dependencies and re-runs annotation
processors on every job. `gradle/actions/setup-gradle@v4` does provide
caching via the `gradle-home-cache-cleanup` and the implicit cache, but
the local repo has no `gradle.properties` controlling `org.gradle.caching=true`,
`org.gradle.parallel=true`, `org.gradle.jvmargs`, or
`org.gradle.configuration-cache=true`. Without those, the cache that
`setup-gradle` provisions is partially unused.

**Fix.** Add a checked-in `gradle.properties` enabling build cache and
configuration cache where the build supports it. Document any
configuration-cache opt-outs.

### M-2 — Matrix is over-specified and not deduplicated

**File**
- `.github/workflows/android.yml` line 25: `os: [ubuntu-latest, windows-latest, macos-15-intel]`
- `.github/workflows/kotlin-jvm.yml` line 25: same

**Why this matters.** Every workflow spins up three runners for every
push. The Android library cannot really exercise the emulator on hosted
CI in a useful way; what we actually want from macOS-15-Intel is
"build passes on Darwin". We can keep three platforms but reduce the
matrix pressure by introducing an `include:` block so the heavy
emulator job runs only on `ubuntu-latest` (and even then only on a
nightly schedule) while the build-only matrix stays at three OSes.

**Fix.** Restructure matrix to: (a) keep build matrix at 3 OSes; (b) gate
the AAR upload + SBOM + signed attestation on ubuntu-latest only; (c)
add a `schedule:`-triggered nightly job for the heavy `connectedCheck`
or lint-deep step.

### M-3 — `pull_request` only targets `main`, never `feat/**`

**Files**
- All workflows.

**Why this matters.** The branch-protection model for this repo gates
merges to `main`. The hardening work is being developed on
`feat/continuity-hardening` and currently the workflows only run on
PRs *into* `main`. This means the hardening itself is not exercised by
its own CI before merge. (Push triggers include `feat/**`, so pushes
into the feature branch do run, but a maintainer who only opens a PR
will get no signal.)

**Fix.** Add `branches: [main, "feat/**"]` to `pull_request:` blocks
everywhere.

### M-4 — Python ports matrix dropped `windows-latest` for an infra reason that should be re-tested

**File**
- `.github/workflows/python-ports.yml` lines 26–35

**Why this matters.** Per the in-line note, the matrix dropped Windows
because of a `setup-python` archive-extraction bug. That bug has been
fixed upstream (setup-python releases after v5.0.0 included the fix).
We should re-enable Windows for Python 3.12 to restore the cross-platform
guarantee.

**Fix.** Re-add a `windows-latest` / `3.12` cell and verify it stays
green; if it regresses, gate it behind a known-broken flag but do not
silently drop the platform.

### M-5 — Conformance vectors are not pinned by content hash

**Files**
- `contracts/conformance/vectors.*.json`

**Why this matters.** A native port satisfies "exactly these vectors".
If a future contributor edits a vector without re-deriving from the
canonical Node implementation, every existing native port will diverge
in a hard-to-debug way.

**Fix.** Add a per-vector-file `sha256` field computed from the
`vectors` array alone (excluding the metadata fields). A CI step
recomputes this hash and fails if it drifts without a matching
`derivedFrom` evidence update.

### M-6 — `local.properties` is checked into git

**File**
- `ecosystems/android/local.properties` (line 1: `sdk.dir=C\:\\Users\\powertech\\...`)

**Why this matters.** `local.properties` is the Android-equivalent of
`.env` — it is machine-specific and should never be committed. The fact
that it contains the local user path is a leak of the contributor's
home directory layout and will break every other contributor's build
on checkout.

**Fix.** Add `**/local.properties` to `.gitignore`, remove the file from
the index with `git rm --cached`, and verify it is gone from the next
commit while preserving a `.local.properties.example` template.
