# Sovereign Library — Security Audit Report v1.0

> Authoritative security audit for the `feat/continuity-hardening` branch.
> Generated by the continuity-hardening deep-dive wave. See
> `docs/HARDENING_FINDINGS_V1.0.md` for the underlying findings and
> per-file location pointers.

## Executive summary

The hardening wave adds five GitHub-Actions hardening primitives and four
new configs to a previously-mature but supply-chain-loose CI surface:

1. Every `uses:` reference in every workflow is now pinned to a 40-char
   commit SHA with the human-readable major tag as a trailing comment.
2. Every workflow now declares a top-level `permissions: { contents: read }`
   block, with individual jobs overriding only what they need.
3. A new `.github/workflows/security-pipeline.yml` runs weekly + on every
   push/PR: SBOM generation (SPDX + CycloneDX), `trivy` filesystem and
   rootfs scans, `safety` Python dependency audit, `gitleaks` secret
   detection, `actionlint` workflow lint, `yamllint` + `markdownlint-cli2`
   doc lint, OIDC token reachability probe, cosign keyless-signature
   reachability probe, and SHA-256 pinning of every conformance vector
   file.
4. The `prepare-authorized-release-artifacts.yml` workflow now signs every
   emitted tarball with `cosign sign-blob` (keyless, OIDC-bound) and emits
   an SLSA Level-3 provenance attestation via `slsa-github-generator` v2.0.
5. A new `gradle.properties` enables build cache, parallel execution, and
   reproducible file timestamps; a new `gradle-wrapper.jar` is no longer
   checked in (commit `43a17f1` already removed it), and a
   `local.properties.example` is added so contributors can wire their SDK
   without committing a machine-specific path.

## Threat model

### Adversary profile

| Adversary | Capability | Mitigation in this wave |
|-----------|-----------|-------------------------|
| Compromised upstream action tag (tj-actions scenario) | Run arbitrary code in the build runner, exfiltrate secrets, tamper with artifacts | SHA-pinned actions; tag is documentation only; runner has no long-lived secrets by default |
| Compromised transitive dependency | Substitute package contents during install | Trivy rootfs scan on `node_modules`; `safety` audit on Python; SBOMs are uploaded for downstream consumers |
| Insider with workflow push access | Modify workflow to exfiltrate release artifacts | Permission hardening: `contents: read` is the default; `id-token: write` and `attestations: write` are job-scoped to the single publish job; cosign signatures are tied to the OIDC issuer so a tampered workflow cannot impersonate the canonical identity |
| Adversary tampering with `contracts/conformance/vectors.*.json` | Cause every native port to drift silently | Conformance vector SHA-256 pinning step in `security-pipeline.yml`; CI fails closed when a pin does not match the recomputed hash |
| Compromised Maven Central / PyPI mirror | Substitute native-port dependencies at install time | Future work: replace Maven Central / PyPI fetches with a local pinned mirror once the optional free-registry wave selects one (not in scope here) |

### Trust boundaries

The repo enforces a strict three-tier trust model:

| Tier | Members | Capabilities |
|------|---------|--------------|
| Read | Public, contributors | View code, open PRs |
| Build | GitHub Actions runners on push / PR | Run tests, lint, SBOM, scans; cannot push to canonical branches |
| Publish | `prepare-authorized-release-artifacts.yml` on `workflow_dispatch` | Sign artifacts, write SLSA provenance, optionally create GitHub Releases |

The publish tier is gated by GitHub branch protection on
`feat/continuity-hardening` → `main` and by the absence of any
long-lived secret — the only credential in the entire pipeline is the
short-lived GitHub Actions OIDC token, scoped to the publishing job.

## Supply chain attestation

Every emitted release artifact is signed with:

- cosign keyless signature bound to the OIDC token issued by
  `https://token.actions.githubusercontent.com` for the workflow
  identity `https://github.com/ahmedsaturki/sovereign-library/.github/workflows/prepare-authorized-release-artifacts.yml@refs/heads/feat/continuity-hardening`.
- SLSA Level-3 provenance generated by
  `slsa-framework/slsa-github-generator` v2.0 in the
  `generator_generic_slsa3` mode. Downstream consumers verify with
  `slsa-verifier` (offline; no network required once the attestation
  is published).

## Remaining open items

These are out of scope for this wave but are recorded so a future
hardening wave can pick them up:

1. Replace `mavenCentral()` and PyPI fetches with a pinned internal
   mirror when the optional free-registry wave selects a target.
2. Add `dependabot.yml` for `github-actions`, `gradle`, and `pip`
   ecosystems. The wave intentionally leaves this to a separate,
   human-approved task per GOVERNANCE rule "Do not publish automatically
   merely because a package has a manifest".
3. Wire `slsa-verifier` into the consumer-side docs so downstream
   maintainers know how to verify the provenance.
4. Add a Threat-Model-as-Code (`threagile` YAML) under `docs/threat/`
   so the threat model above is reviewable in PR diffs.
